# 0.6.1 视频拖动响应修复

日期：2026-10-24。用户反馈裁剪时拖动手柄不跟手。

## 根因与改动

1. 原 `Seek` 先调用 `Pause` 发出 Changed，再设置媒体位置并第二次发出 Changed。第一条通知携带旧位置，导致指针在每次定位时短暂回跳。现在暂停位置由请求值维护，一次位置修改只通知一次；后台解码位置不会覆盖拖动中的 UI 请求。
2. 暂停状态的 50ms 定时器仍不断通知界面刷新。现在只在播放时运行播放时钟，暂停后没有空通知。
3. 拖动每个鼠标事件都请求解码。现在拖动时使用 50ms 的最新值合并队列，最多约每 50ms 请求一次最新位置；松手立即提交最后值。关闭、保存、失败会清理待处理请求。
4. 手柄从固定时间轴坐标计算目标位置，避免相对于正在移动的 Thumb 反复累加；位置使用 TranslateTransform，避免每次拖动重新排列控件。
5. 胶片、刻度、字体与轮廓缓存为 DrawingGroup，只在尺寸、DPI、视频时长或缩略图变化时重建；拖动只绘制选区遮罩和移动控件。位置未变时不刷新。

## 前后对比

使用同一台电脑、同一段 33 秒真实录屏备份、相同测试窗口。数值是本次单次诊断记录，不代表所有硬件或视频的帧率。

| 指标 | 0.6.0 | 修复后 |
| --- | --- | --- |
| 连续 240 次选区起点更新耗时 | 162.62ms | 23.55ms |
| 上述更新触发的通知 | 480 | 240 |
| 携带旧位置的回跳通知 | 240 | 0 |
| 暂停 600ms 的空通知 | 10 | 0 |
| 120 次时间轴位置更新及离屏渲染 | 179.84ms | 139.81ms |
| 上述渲染测试的线程分配字节 | 4,950,192 | 721,512 |

结果文件：`artifacts/scrub-before/results.txt`、`artifacts/scrub-after/results.txt`。批量位置更新耗时约减少 85.5%，渲染测试分配约减少 85.4%。离屏渲染包含 RenderTargetBitmap 的公共开销，不能换算为真实桌面 FPS。

## 验证

- 5 项专项断言通过：无旧位置通知、暂停无空刷新、拖动突发立即更新 UI 且不逐次提交原生 Seek、松手立即提交最终位置、持续拖动定期解码最新位置。
- 14 项视频回归全部通过，覆盖监听、播放/暂停/继续/结尾重播、裁剪保存、取消、时间输入同步、失败恢复选区、五种格式音轨保留、损坏媒体保护。结果：`artifacts/scrub-video-regression/results.txt`。
- 真实鼠标拖动：起点从 2.5 秒拖至 6.629 秒，再反向拖至 4.371 秒；手柄落点、时间字段、播放指针及暂停预览一致。使用隔离副本，未裁改用户视频。
- 构建无警告、无错误。发布包：`dist/Liangtu-0.6.1-Windows-x64-portable.zip`。

重跑专项诊断可使用 `scripts/test-video-scrub.ps1 -SourceVideo <至少10秒的视频路径>`。脚本显示隔离窗口并测量 UI 行为，只读源视频。

## 边界

拖动时优先保持手柄和时间字段即时响应，视频帧预览按最新请求合并更新；重编码较重或超高分辨率视频仍可能受 Windows 解码器性能限制。松手会立即请求最终帧，裁剪导出仍按所选时间调用原有 FFmpeg 流程。
